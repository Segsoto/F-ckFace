# Trabajo y documentación del proyecto

La documentación central y la bitácora están en `docs/documentacion-proyecto.txt`.
Leer ese archivo y `docs/calidad.md` antes de modificar el proyecto. Consultar
`docs/manual-uso.txt` para los procedimientos del panel.

Por instrucción del propietario, toda modificación debe quedar documentada:

1. Revisar el estado de Git y conservar cambios ajenos.
2. Actualizar las secciones de la documentación central afectadas por el cambio.
3. Añadir una entrada a su bitácora con fecha de Costa Rica, solicitud, motivo,
   archivos, pasos realizados, resultado, verificaciones, limitaciones, estado
   de publicación y pendientes. Registrar solo acciones y resultados comprobados.
4. Actualizar el manual de uso si cambia un procedimiento del usuario y el README
   si cambia la configuración o el mantenimiento.
5. Ejecutar las comprobaciones adecuadas al alcance y anotar su resultado. No
   declarar una publicación, una migración aplicada o una revisión en producción
   sin evidencia de haberlas realizado.
6. Antes de terminar, revisar el diff y comprobar que documentación y código
   describen el mismo comportamiento. No copiar credenciales ni datos personales
   a los documentos, ejemplos o bitácora.

Mantener un único registro central; añadir las entradas sin borrar el historial.
Los datos variables deben llevar fecha y contexto. No inventar fechas ni resultados
para cambios antiguos: documentarlos como inventario reconstruido desde el código.

Respetar las rutas públicas y el nombre `NewDrop.html` registrado en Git; Windows
puede mostrarlo con otra capitalización. `Camisadel10/` pertenece a otra aplicación:
no mezclar su configuración, datos o herramientas con F-ck Face.

Las herramientas de limpieza histórica apuntan a un proyecto Supabase distinto del
configurado actualmente. Leer `docs/limpieza-fotos.md` antes de utilizarlas; una
tarea de documentación o verificación no autoriza a ejecutar borrados reales.
