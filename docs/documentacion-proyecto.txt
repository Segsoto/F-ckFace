01. CÓMO MANTENER ESTE DOCUMENTO
------------------------------
Este archivo es la referencia central para entender y modificar F-ck Face.
AGENTS.md establece la obligación de actualizarlo en futuras tareas de Codex.

En cada cambio:
1. Leer este documento, docs/calidad.md y el código afectado.
2. Revisar git status y separar los cambios existentes del trabajo solicitado.
3. Definir qué comportamiento cambia y qué pantallas, módulos y datos intervienen.
4. Realizar la modificación y las comprobaciones pertinentes.
5. Actualizar la descripción del sistema en las secciones afectadas.
6. Añadir una entrada fechada a la sección 19 usando la plantilla de la sección 20.
7. Actualizar docs/manual-uso.txt si cambia la operación del panel.
8. Actualizar README.md si cambia la configuración, instalación o mantenimiento.
9. Revisar el diff y registrar el estado real de publicación y pendientes.

Escribir qué se hizo, por qué, dónde, cómo se verificó y qué falta. Los intentos
fallidos relevantes se registran con su resultado, sin presentarlos como éxitos.
No borrar entradas anteriores ni convertir pendientes en tareas completadas sin
evidencia. No inventar una cronología de modificaciones antiguas.
Registrar fechas en Costa Rica; los datos técnicos UTC deben identificarse como UTC.
No almacenar contraseñas, tokens, service_role, claves privadas o datos de clientes.
Los ejemplos deben usar marcadores como <UUID_ADMIN> y <DOMINIO>.
Un commit prueba que el cambio está en Git, no que se haya publicado.


02. QUÉ HACE EL PROYECTO Y ARQUITECTURA
-------------------------------------
Catálogo de prendas con acceso anticipado mediante drops. Las consultas se coordinan
por WhatsApp. El sitio no implementa carrito, cobro en línea, envío de correos ni
cuentas para compradores.

Capas:
- HTML: estructura de la tienda, acceso exclusivo, panel y página de error.
- CSS: presentación y adaptación a tamaños de pantalla.
- JavaScript de página: eventos, lectura de datos y actualización de la interfaz.
- JavaScript compartido: medidas, imágenes, compresión, ventas y auxiliares.
- Supabase Auth: inicio de sesión de administradores.
- Supabase PostgreSQL: productos, drops, autorización y colas de limpieza.
- Supabase Storage: fotos originales o comprimidas de las prendas.
- Hosting estático: HTML, CSS, JavaScript, imágenes locales y videos.
- Herramientas locales: servidor de desarrollo, miniaturas y limpieza histórica.

Flujo público:
Visita -> app.js -> RPC de catálogo -> productos publicados -> tarjetas ->
RPC de verificación del producto -> detalle y miniaturas -> consulta por WhatsApp.

Flujo exclusivo:
NewDrop.html -> metadatos del drop -> contraseña -> RPC que valida horario y hash ->
productos new_drop del drop autorizado -> filtros, detalle y WhatsApp.

Flujo administrativo:
Auth -> comprobación en admin_profiles -> lectura/escritura con RLS -> inventario,
programación, publicación, venta e historial -> Storage API para las fotos.

El navegador usa el SDK Supabase directamente. No hay un backend Node propio en
producción ni un proceso de compilación de la web. El servidor Node de tools/ es
solo una herramienta local para servir archivos.

- Siete categorías principales y botón para volver al catálogo completo.
- Tarjetas con foto, nombre, talla, condición, precio y estado de disponibilidad.
- Descuento porcentual y precio anterior cuando original_price > price.
- Mensajes de catálogo vacío, categoría vacía y error de carga.
- Contador informativo para la apertura pública del próximo drop.
- Detalle de producto con descripción, medidas, precio, galería y consulta.
- Enlace directo index.html?prenda=<UUID_PRODUCTO>.

Carga de datos:
1. Ejecuta release_due_drops.
2. Consulta get_public_catalog y get_current_drop en paralelo.
3. Renderiza las prendas published, ordenadas por la respuesta del servidor.
4. Si hay parámetro prenda, busca la pieza y abre su detalle.

Antes de abrir el detalle, get_public_product vuelve a comprobar que la prenda
sigue publicada. Una venta o retirada puede hacer que deje de estar disponible.
Los estados reserved y payment_pending conservan visibilidad pero bloquean la
consulta desde el botón de la ficha y muestran el aviso correspondiente.

El filtro público actual es por categoría. La búsqueda y el filtro por talla
pertenecen a New Drop y al panel; no atribuirlos a index.html.

WhatsApp:
- Mensaje de prenda: nombre, precio y enlace al detalle.
- Consulta general: mensaje general, sin ID de prenda.
- wa.me precarga texto; el visitante realiza el envío en WhatsApp.
- No adjunta archivos ni genera una miniatura específica del producto en WhatsApp.
- Compartir el enlace no reserva automáticamente la prenda.


06. NEW DROP Y VISTA PREVIA ADMINISTRATIVA
----------------------------------------
Archivos: NewDrop.html, assets/js/pages/newdrop.js, shared/drop-preview.js.

Antes de la apertura exclusiva:
- Muestra contador y formulario de acceso.
- El botón de acceso permanece deshabilitado.
- No carga prendas exclusivas mediante el RPC de contraseña.

Durante la ventana exclusiva:
- get_exclusive_products valida drop, contraseña, actividad y horario en SQL.
- Si concede acceso, muestra las prendas new_drop vinculadas a ese drop.
- Categorías disponibles y sus cantidades se calculan a partir de esas prendas.
- Todas, búsqueda, talla, limpiar filtros y contador de resultados.
- Búsqueda normalizada: minúsculas, espacios y acentos.
- Detalle con fotos, miniaturas cuando existan, precio y medidas.
- Al abrir una prenda vuelve a leer las prendas autorizadas para comprobarla.

Persistencia del acceso comunitario:
- Clave localStorage: ff-exclusive-drop-<UUID_DROP>.
- Guarda password y expiresAt, igual a la apertura pública.
- Se valida de nuevo al recuperar el acceso; no sustituye al control del servidor.
- Al llegar a la apertura pública elimina la entrada y vuelve a cargar el estado.
- Esta contraseña comunitaria es independiente de las credenciales de Auth.

Apertura pública:
- El contador invoca release_due_drops y recarga New Drop.
- La sección exclusiva se cierra; las prendas publicadas están en index.html.
- NewDrop.html?prenda=<UUID> redirige a index.html si esa prenda ya es pública.
- Sin drop activo se muestra el mensaje correspondiente.

Vista previa administrativa:
- Enlace desde el panel: NewDrop.html?preview=admin.
- Necesita sesión Auth y fila del usuario en admin_profiles.
- Lee directamente el drop activo y sus prendas new_drop bajo los permisos RLS.
- Permite revisar antes de la apertura exclusiva sin contraseña comunitaria.
- No ejecuta release_due_drops ni inicia el contador de publicación automática.
- No modifica fechas, estados ni datos de las prendas.
- Compartir esa URL no concede permisos de administrador.

Enlaces de WhatsApp:
- Conservan solo el enlace de prenda de New Drop.
- No añaden password ni preview=admin al enlace compartido.


07. ADMINISTRACIÓN: MÓDULOS Y OPERACIONES
---------------------------------------
Archivos: admin.html, assets/js/pages/admin.js, assets/css/admin.css.

Sesión:
- signInWithPassword recibe correo y contraseña de Supabase Auth.
- La autorización exige una fila propia en admin_profiles.
- Un usuario autenticado sin perfil autorizado no entra al panel.
- setup comprueba la sesión al cargar; logout limpia campos de contraseña y sesión.
- Mostrar/ocultar una contraseña solo cambia la presentación del campo.

Navegación por módulos:
- Programación del drop: dropModule.
- Alta/publicación de prendas: publishModule.
- Inventario activo y filtros: publishedModule.
- Historial, ingresos y fichas: salesModule.
El inventario activo incluye new_drop y published aunque su ID sea publishedModule.

Programación del drop:
- Nombre, apertura exclusiva, apertura pública, contraseña y nota opcional.
- Creación/edición mediante save_managed_drop.
- Crear exige apertura exclusiva futura; pública posterior a exclusiva y al momento
  de guardar. Editar permite conservar una apertura exclusiva que ya ocurrió.
- El servidor serializa la creación/edición para conservar un único drop activo.
- Contraseña vacía al editar conserva la existente.
- Consulta administrativa de contraseña guardada en drop_passwords.
- Contraseñas antiguas sin fila consultable deben guardarse de nuevo para mostrarse.
- Desactivar mediante deactivate_drop conserva prendas sin publicarlas ni moverlas.
- El panel carga el drop activo y ofrece su vista previa.

Alta de prenda:
- Nombre, precio entero CRC, categoría, talla, condición, descripción y medidas.
- Destino NEW DROP: exige drop activo, status=new_drop y drop_id=ID del drop.
- Destino TIENDA PÚBLICA: status=published y drop_id=null; no exige drop activo.
- Admite de una a siete fotos JPG, PNG o WebP, hasta 10 MiB de entrada por foto.
- Comprime en el navegador antes de subir; ver sección 12.
- Genera rutas con UUID del administrador, timestamp, UUID aleatorio y nombre limpio.
- Registra las rutas en deleted_product_images antes de subir.
- available_at de esa tarea se difiere una hora para proteger una carga en curso.
- Sube secuencialmente, crea la fila products y cierra la tarea de carga.
- Un fallo de subida o guardado intenta limpiar los archivos; conserva la tarea si
  queda trabajo pendiente. Una foto referenciada por un producto guardado se conserva.
- Muestra progreso, peso final y porcentaje de ahorro cuando corresponda.

Inventario:
- Lista de prendas que no están sold.
- Filtros por texto, talla, categoría, precio mínimo/máximo y descuento.
- Contador de resultados y limpiar filtros.
- Cambio de disponibilidad: available, reserved o payment_pending.
- Edición de nombre, precio, categoría, talla, condición, descripción y medidas.
- El editor admite reemplazar el conjunto completo de fotos con 1 a 7 originales.
  Sin selección conserva las fotos actuales. La primera nueva foto es la portada.
- Usa la misma preparación en alta calidad del alta, con rutas nuevas sin upsert.
- Registra las fotos anteriores para limpieza antes de guardar y comprueba status
  y updated_at para detectar cambios de otra sesión. Si falla, revisa referencias
  antes de limpiar cargas nuevas; protege las fotos que sí quedaron guardadas.
- Limpia fotos anteriores sin referencias después del guardado; conserva tareas
  pendientes si falla Storage. Los reintentos se ofrecen después de una hora.
- Durante el guardado bloquea controles y cierre del editor. No cambia destino/drop.
- El cambio de disponibilidad conserva la fila devuelta por el servidor, incluido
  updated_at, para poder editar después sin un conflicto causado por la misma sesión.

Descuentos:
- Al bajar el precio conserva el mayor entre el precio anterior y original_price.
- original_price debe ser mayor que price para mostrar descuento.
- Al alcanzar o superar el precio anterior, se elimina la rebaja.
- Quitar descuento se aplica al guardar la edición.

Registrar venta:
- VENDIDA abre un formulario con el monto recibido.
- Monto: entero no negativo en CRC; puede diferir del precio publicado.
- Guarda sold, sold_at, sale_price y sale_origin_status.
- Conserva solo la primera URL de foto y registra las adicionales para limpieza.
- Condiciona la escritura al estado y updated_at leídos para detectar conflictos.
- La venta permanece registrada aunque falle posteriormente la limpieza de Storage.
- Las piezas sold salen de los catálogos y del inventario activo.

Historial e ingresos:
- Total bruto acumulado y cantidad de prendas vendidas.
- Resúmenes actuales y desglose por semana, quincena y mes.
- Semana de lunes a domingo; quincenas del 1 al 15 y del 16 al fin de mes.
- Períodos y fechas de venta calculados en America/Costa_Rica.
- Los importes proceden de sale_price; no son utilidad ni incluyen cálculo de costos.
- Ficha con foto principal, descripción, medidas, precio publicado, monto y fechas.
- Conservar solo una foto en ventas limpia ventas antiguas y pendientes.

Revertir venta:
- Primero debe completarse la limpieza pendiente de esa venta.
- Resta la venta de los resúmenes al limpiar los campos de venta.
- Recupera new_drop solo si su drop original sigue activo y no abrió al público;
  en otro caso restaura published.
- availability vuelve a available.
- No recupera fotos adicionales que ya fueron borradas.

Eliminar prenda:
- Pide confirmación y llama delete_product_for_admin.
- Retira la fila y registra URLs para limpieza en una transacción de PostgreSQL.
- El navegador usa Storage API para borrar los objetos.
- No equivale a vender y no suma ingresos ni conserva una ficha de venta.
- Ante fallos, ofrece REINTENTAR LIMPIEZA DE FOTOS.


08. MÓDULOS JAVASCRIPT COMPARTIDOS
---------------------------------
measurements.js -> window.ProductMeasurements
- fields(category): selección de campos de medidas.
- editor(container, category, product, original): crea controles numéricos y conserva
  medidas históricas no seleccionadas bajo MEDIDA ANTERIOR cuando aplica.
- values(container): valores numéricos o null desde el formulario.
- display(product): reconstruye las medidas visibles en el detalle público/exclusivo.
- Medidas en cm, opcionales; inputs de 0 a 9999,99 con paso 0,01.
- Pantalones: length_cm, waist_width_cm, inseam_cm.
- Bolsos/mochilas: height_cm, width_cm, depth_cm.
- Jackets y categoría anterior abrigos: largo, pecho, ancho y largo de manga.
- Otras categorías: largo y pecho.
- inseam_cm conserva su nombre histórico en datos y se rotula ANCHO DE PIERNA.
  Cambiar el rótulo no convierte valores históricos de entrepierna en ancho.

product-images.js -> window.ProductImages
- prepare(root): observa carga/error de imágenes de producto y de galería.
- setSource(img, src): establece URL y decoding=async; actualiza estado visual.
- thumbnailFor(product, source): busca miniatura por URL exacta dentro de la prenda.
- renderGallery(gallery, mainImage, product, images): botones con previews, selección
  activa y aria-pressed; oculta navegación si solo hay una foto.
- Preview de 62x62 CSS, lazy, prioridad low y alt vacío porque el botón tiene nombre.
- Fallback de miniatura ausente a original una vez; no genera un bucle de errores.
- No reasigna la foto grande cuando se pulsa la selección que ya está activa.

product-thumbnails.js -> window.ProductThumbnails
- Archivo generado, no una lista manual de productos.
- Claves UUID de prenda; source/thumbnail para portada; gallery con pares
  source/thumbnail para las demás vistas.
- Las URLs originales sirven para detectar fotos cambiadas y reordenadas.

image-compression.js -> window.ImageCompression
- prepare(files, onProgress): valida toda la selección y procesa una foto a la vez.
- compress(file): decodifica, reduce dimensiones/peso y entrega File listo para subir.
- MAX_BYTES=1500000; MAX_DIMENSION=2400.
- Calidad de codificación: 0,92 / 0,90 / 0,88, antes de reducir dimensiones.
- WebP preferido; JPEG alternativo si el navegador no codifica WebP.
- Libera bitmap/canvas al terminar o fallar; rechaza fotos no preparables.

drop-preview.js -> window.DropPreview
- load(client): autoriza al administrador y obtiene drop activo y sus prendas.
- products(client, dropId): autoriza y lee products de ese drop con status=new_drop.
- No concede permisos ni ignora RLS; usa la sesión existente.

sales-report.js -> window.SalesReport y exportación CommonJS en Node
- period(value, kind): inicio, clave y nombre de un período.
- build(sales, now): suma importes y cuenta ventas por week, fortnight y month.
- Conserva un grupo para el período actual incluso si no tiene ventas.
- Omite fechas de venta inválidas al agrupar.

sale-photos.js -> window.SalePhotos y exportación CommonJS en Node
- plan(product): primera foto conservada y fotos extra sin duplicados.
- storagePath(url, baseUrl): acepta solo URLs esperadas del bucket del proyecto;
  rechaza rutas ajenas, consultas, fragmentos y segmentos de navegación.
- cleanup(client, product, baseUrl): procesa image_cleanup_pending de una venta;
  protege primera foto y fotos compartidas; conserva pendientes ante fallos.
- cleanupDeleted(client, job, baseUrl): limpia una tarea de eliminación/carga;
  comprueba referencias antes de borrar y cierra o actualiza la tarea.
- Las consultas y los borrados de Storage son operaciones separadas; no constituyen
  una transacción distribuida entre PostgreSQL y Storage.

password-toggle.js
- Envuelve inputs password y añade botón con aria-controls y aria-pressed.
- Cambia password/text sin alterar su valor; hide-password vuelve a ocultarlo.
- Debe cargarse después de los campos HTML y antes de los eventos que lo utilizan.

page-loader.js -> window.StorePageLoader
- start, ready y finish controlan el overlay de carga.
- Espera imágenes de cabecera/hero/categorías y hasta ocho fotos iniciales del grid.
- Esas imágenes iniciales se ponen eager; las demás conservan su carga diferida.
- Límite de espera de ocho segundos y salida en pagehide.
- Bloquea Tab mientras el overlay está activo y evita quedar esperando por siempre.
- Se carga temprano en index.html y NewDrop.html; no interviene en admin.html.

Orden de scripts:
- Página pública: loader temprano; después SDK, config, medidas, imágenes,
  mapa de miniaturas y app.js.
- New Drop: loader temprano; después SDK, config, toggle de contraseña, medidas,
  imágenes, mapa, vista previa y newdrop.js.
- Admin: SDK, config, toggle, medidas, compresión, mapa, reportes, fotos y admin.js.
Conservar este orden al incorporar dependencias globales nuevas.


09. MODELO DE DATOS Y ESTADOS
----------------------------
public.products:
- id: UUID de la prenda.
- name: nombre obligatorio, de 1 a 160 caracteres según el esquema.
- price: entero no negativo, colones costarricenses.
- original_price: null o importe positivo mayor que price.
- category: identificador permitido por el CHECK de la tabla.
- size, condition, description: textos descriptivos opcionales.
- image_urls: arreglo de URLs de fotos; la primera es portada y foto conservada.
- drop_id: referencia opcional a drops, ON DELETE SET NULL.
- status: new_drop, published o sold.
- availability: available, reserved o payment_pending.
- length_cm, chest_width_cm: largo y ancho de pecho.
- sleeve_width_cm, sleeve_length_cm: ancho y largo de manga.
- waist_width_cm, inseam_cm: cintura en plano y campo histórico de pantalones.
- height_cm, width_cm, depth_cm: alto, ancho y fondo para bolsos.
- sale_price, sold_at, sale_origin_status: datos de venta; obligatorios al estar sold,
  y null en los demás estados por products_sale_check.
- image_cleanup_pending: arreglo de URLs que quedan por limpiar en ventas.
- created_at, updated_at: control temporal; updated_at participa en escrituras
  condicionales de venta, reversión y limpieza.

Categorías principales:
jacket_damas, jacket_caballeros, pantalones, chalecos, tallas_plus, ropa_ninos,
mochilas (etiqueta administrativa Bolsos / Mochilas).
Compatibilidad con categorías antiguas: camisas, abrigos, buzos, accesorios, otros.
No borrar ni convertir categorías antiguas sin revisar los productos existentes.

public.drops:
- id, created_at: identidad y fecha de creación.
- name: nombre, predeterminado New Drop.
- exclusive_at: inicio del acceso comunitario.
- public_at: inicio público.
- release_at: fecha histórica mantenida por compatibilidad, igual a public_at al
  guardar con el RPC actual.
- access_password_hash: hash usado para validar la contraseña del acceso exclusivo.
- description: nota opcional.
- is_active: actividad del drop.

public.admin_profiles:
- user_id: UUID de Auth autorizado, PK y FK a auth.users con ON DELETE CASCADE.
- created_at: fecha de autorización.

public.drop_passwords:
- drop_id: PK/FK a drops, con ON DELETE CASCADE.
- password: contraseña comunitaria consultable por administradores autorizados.
El hash en drops no es la única representación de esa contraseña: existe esta copia
en texto consultable para el panel. No describir el sistema como solo hash.

public.deleted_product_images:
- id: identidad de la tarea de limpieza.
- product_id: UUID de referencia de la prenda o provisional de una carga.
  No exige que la fila products siga existiendo.
- urls: fotos a revisar/borrar.
- available_at: momento desde el cual se ofrece el reintento.
- created_at: creación de la tarea.

Transiciones:
- Alta exclusiva: new_drop + drop_id activo.
- Apertura pública: new_drop -> published para las prendas de ese drop.
- Alta directa: published + drop_id=null.
- Apartado/proceso: cambia availability, sin cambiar status.
- Venta: new_drop/published -> sold, registra origen y monto/fecha.
- Reversión: sold -> new_drop o published según vigencia del drop original.
- Eliminación: retira la fila activa y deja una tarea de limpieza de fotos.


10. FUNCIONES SQL, AUTORIZACIÓN Y STORAGE
---------------------------------------
RPC públicos o utilizados por visitantes:
- release_due_drops(): publica prendas new_drop de drops activos cuya fecha pública
  venció y desactiva esos drops. SQL toma la hora del servidor.
- get_current_drop(): metadatos del próximo drop activo, sin contraseña guardada.
- get_public_catalog(): productos con status=published.
- get_public_product(p_product_id): una pieza published, si existe.
- get_exclusive_products(p_drop_id,p_password): valida ventana exclusiva, actividad
  y hash; devuelve prendas new_drop del drop autorizado.

RPC administrativos:
- is_admin(): verifica auth.uid contra admin_profiles.
- save_managed_drop(p_drop_id,p_name,p_exclusive_at,p_public_at,p_password,
  p_description): creación o edición del drop, hash y contraseña consultable.
- deactivate_drop(p_drop_id): desactiva sin transferir/publicar prendas.
- delete_product_for_admin(p_product_id): retira prenda no sold y deja tarea de fotos.
- save_active_drop(p_exclusive_at,p_public_at,p_password,p_description): RPC anterior
  presente por compatibilidad; el panel actual usa save_managed_drop.

Protecciones descritas por los SQL del repositorio:
- Tablas administrativas con RLS y políticas basadas en is_admin.
- admin_profiles permite al usuario autenticado consultar su propia autorización.
- anon no dispone de acceso directo a las tablas principales; el público usa RPC.
- drop_passwords solo ofrece SELECT a administradores mediante su política.
- RPC administrativos sensibles comprueban autorización dentro de la función.
- Algunas funciones son SECURITY DEFINER: revisar permisos, search_path y resultado
  completo al editarlas; no suponer que el frontend impone su seguridad.

Storage:
- Bucket product-images, configurado como público en supabase-schema.sql.
- Inserción/actualización exige administrador y prefijo del UUID de quien sube.
- Eliminación permitida a administradores autorizados del bucket, incluso de fotos
  que subió otra cuenta administradora.
- Frontend usa APIs de Storage; no borrar filas storage.objects mediante SQL.
- Foto pública y fila privada son capas distintas: conocer la URL de una imagen
  pública permite acceder al objeto aunque la prenda no esté en el catálogo.
- La copia de miniaturas en el hosting no se elimina al borrar una foto de Storage.

Gestión de accesos:
1. Crear/invitar administrador desde Supabase Auth.
2. Añadir su user_id a public.admin_profiles con una operación administrativa.
3. Comprobar entrada del usuario autorizado y rechazo de otro usuario sin perfil.
4. Gestionar contraseñas en Auth, fuera de este archivo y del repositorio.
No afirmar que MFA, límites de intentos o registros públicos estén configurados
porque aparezcan como recomendación en la documentación: requieren revisión real.

12. IMÁGENES, COMPRESIÓN, MINIATURAS Y CACHÉ
-----------------------------------------
Hay tres tamaños/propósitos diferentes:
1. Foto almacenada en Storage: la que muestra el detalle de la prenda.
2. Portada local: WebP hasta 800x1080, calidad 88, sin ampliar la fuente.
   Se usa en tarjetas cuando coincide la URL original; cover_version=2.
3. Miniatura de galería: WebP hasta 128x172 para botones de vista previa de 62x62.

Compresión de cargas nuevas:
- Entrada JPG/PNG/WebP; 1 a 7 archivos, cada uno hasta 10 MiB.
- Salida máxima 1500000 bytes (1,5 MB decimal) por foto y lado mayor de 2400 px.
- Aplica tanto al alta como al reemplazo desde Editar.
- Prefiere calidad WebP 0,92, 0,90 o 0,88 para conservar detalles de tejido/etiquetas.
- Mantiene proporciones; no recorta ni amplía.
- Conserva archivo pequeño si cumple límites y no requiere recompresión.
- Prueba calidad WebP; usa JPEG si el navegador no produce WebP.
- Si no alcanza el límite de peso, reduce dimensiones un 15% por intento, hasta
  seis intentos, manteniendo ese rango de calidad de codificación.
- Un archivo ilegible/no reducible detiene la preparación, sin subir el original.
- La compresión ocurre en el cliente; no transforma fotos históricas existentes.
- Las subidas usan cacheControl=86400 y rutas nuevas, sin upsert.
- Es un límite del panel, no un límite de tamaño del bucket en el servidor.

Generación de miniaturas:
  python tools/build-product-thumbnails.py
- Lee config.js para URL y clave pública.
- Consulta get_public_catalog: solo las prendas públicas actuales.
- Acepta fuentes HTTPS del proyecto configurado y bucket público product-images.
- Reutiliza portada existente si source y cover_version=2 coinciden y existe.
- Regenera las portadas antiguas desde Storage; no amplía una portada comprimida.
- La primera miniatura puede generarse desde esa portada sin descargar su original.
- Descarga originales únicamente para miniaturas/portadas que faltan.
- Procesa hasta cuatro prendas simultáneamente y limita las respuestas a 10 MB.
- Respeta orientación EXIF; portadas WebP quality=88 y previews quality=60.
- Registra fallos por imagen. No aumenta la resolución de una fuente pequeña.
- Los nombres incluyen UUID y hash SHA-256; en portadas el hash también incorpora
  versión, dimensiones y calidad para invalidar la caché al cambiar el perfil.
- Reescribe product-thumbnails.js con el mapa del catálogo público consultado.
- No borra automáticamente archivos locales de productos retirados del catálogo.

Comportamiento de la galería:
- Miniaturas visibles al entrar en la prenda, con lazy/decodificación asíncrona.
- Foto principal se carga al abrir la ficha; las demás fotos grandes al seleccionarlas.
- La selección activa no provoca una nueva asignación de su foto grande.
- Si no hay miniatura, usa la URL original con lazy y prioridad baja.
- Si falla una miniatura local, intenta la URL original una sola vez.
- Se valida source exacta, por lo que un cambio/orden de fotos no intercambia vistas.

Publicación de miniaturas:
- Subir img/product-thumbs/ y product-thumbnails.js junto al código de galería.
- Después de añadir/cambiar fotos públicas, regenerar y publicar ambos recursos.
- No hay generación automática desde el panel ni al abrir una prenda.
- Drops todavía exclusivos usan originales hasta disponer de una solución específica;
  el generador público no los incluye ni publica sus datos en el mapa.
- Miniaturas con hash admiten caché larga/immutable en hosting; mapa y código deben
  revalidarse para recoger cambios. Son pautas de configuración, no reglas ya
  aplicadas por un archivo de hosting del repositorio.
- tools/dev-server.cjs usa no-store deliberadamente durante desarrollo.
- Una imagen cacheada todavía puede consumir tráfico del proveedor. Miniaturas
  reducen bytes; no garantizan consumo nulo ni un ahorro porcentual universal.

17. DIAGNÓSTICO Y LIMITACIONES CONOCIDAS
--------------------------------------
Catálogo no carga:
- Revisar error concreto en consola/red, config.js, RPC, esquema y permisos.
- Una prueba local de scripts no confirma una migración aplicada en Supabase.

Usuario Auth no entra al panel:
- Comprobar admin_profiles para su UUID y sesión; Auth sin autorización no basta.

404 de RPC o columnas desconocidas:
- Comprobar proyecto y versión de SQL aplicada; revisar recarga de esquema API.
- Error gen_salt/crypt: scripts usan pgcrypto en extensions; revisar instalación.

Prendas exclusivas no se publican:
- Revisar public_at/release_at, is_active, status y drop_id.
- release_due_drops se invoca desde visitas/cargas normales y el contador de New
  Drop. No hay tarea Cron configurada en los scripts revisados.
- Sin visitas en el instante del lanzamiento, puede publicarse en la siguiente
  carga. El contador público de index.html cambia su texto al vencer; no recarga por
  sí mismo el catálogo en ese tick. Recargar ejecuta la publicación y lectura.
- La vista previa administrativa de New Drop no ejecuta esa publicación.

Preview ausente o pesada:
- Comprobar correspondencia exacta source, archivo local y despliegue del mapa.
- Regenerar miniaturas públicas; si no existe derivado, fallback es la foto original.
- No asumir que lazy limita el tamaño descargado: solo difiere el momento.

Ventas o limpieza no guardan:
- Comprobar SQL de ventas, RLS, estado y updated_at frente a edición concurrente.
- Venta puede haberse guardado aunque la limpieza falle; revisar historial/pendientes.
- Una foto compartida no debe borrarse. Storage y filas tienen verificaciones propias.

HTTP 402/cuota de Storage:
- Verificar estado actual del proyecto en Supabase.
- La herramienta histórica no evita restricciones de cuota.
- Borrar almacenamiento no elimina tráfico que ya se consumió en un ciclo.
- Las cifras de docs/limpieza-fotos.md son históricas y pertenecen a otro proyecto.

Limitaciones observadas, no mejoras implementadas:
- Miniaturas se generan manualmente y solo para catálogo público.
- Archivos locales antiguos de miniaturas no se limpian automáticamente.
- Sin Cron independiente de visitas ni actualización Realtime de inventario público.
- Estado de disponibilidad no se convierte en reserva transaccional al consultar.
- Las fotos antiguas con detalle perdido necesitan originales para recuperarlo.
  El reemplazo del editor permite subirlos; aumentar píxeles no recupera información.
- Un conjunto reemplazado no dispone de deshacer: se limpian las fotos anteriores
  sin referencias. Conservar originales fuera del panel antes de sustituirlas.
- El botón de alta conserva texto genérico AGREGAR A NEW DROP aun para destino
  público; la fila guardada sí respeta el destino seleccionado.
- Sin configuración de hosting/caché versionada en los archivos revisados.
- SDK externo fijado a versión mayor; no hay versión exacta en un lockfile.
- El manual previo contenía una contraseña: se retira en DOC-002. Retirarla del
  archivo actual no borra copias o historial Git; su rotación requiere gestión Auth.
